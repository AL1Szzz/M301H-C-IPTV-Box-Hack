# 康佳电视 ADB「时连时断」根因分析

> 基于 `分析该项目_2026-10-25_16-57.md`（Qoder 会话导出，25,214 行）中的全部实测日志，
> 并叠加了本机当前状态复核（17:02 实扫 `192.168.50.0/24:5555`，无应答）。
> 设备：康佳 Android TV（MStar `mstar_mci.0` 平台，Android 4.4，1080p），原 `192.168.50.17` → 现 `192.168.50.104`。

---

## 一、一句话结论

**不是"ADB 不稳定"，是"设备一直在崩溃重启，而 ADB 的可用窗口被切成了一串随机的碎片段"。**
你看到的「有时连得上」，是恰好撞上了一片碎片；「有时连不上」，是那次开机碎片根本没出现，或者出现了但你没来得及用它。
此外还有两类"假性连不上"：**找错门**（IP/MAC 漂移）和**自己耗光**（连接握手 + `adb root` 太慢）。

## 四、「时连时断」的六层原因（按贡献度排序）

### 第 1 层 · 高置信：窗口是两个时钟的赛跑

- **时钟 A**：init → adbd 起来 + 以太网 link 协商 + `dhcpcd` 拿到 IP。你实测过 `dhcpcd` 是 PID 1（init）拉起的，所以**理论上不依赖安卓框架**。
- **时钟 B**：`system_server` 崩溃 → 电视黑屏 / 自动断电。你的描述：上电约 **20 秒**后背光亮，**1~2 分钟后**黑屏。
- **只有 A 完成且 B 尚未发生，窗口才存在**。上限约 60~120 秒，实际常是 3~26 秒。
- 当 B 抢在 A 前面发生（框架还没起来就断电），**连端口都不会出现** —— 这是绝大多数"连不上"的真相。

### 第 2 层 · 高置信：adb 要"三步走"，而多数窗口装不下这三步

一次窗口里完整链路是：

```
TCP 探测 → adb connect 握手 → adb devices 出现 device → adb root(adbd 重启!) → 等 3~5 秒重连 → id 确认 uid=0 → 执行命令 → 验证
```

- `adb root` 会**杀掉并重启 adbd**，重启期间 transport 是 `offline` / `not found`。16:06:48 的 `not root yet: device '...' not found` 就是这个阶段被崩溃打断。
- 13:31 那次是唯一走完全程的，用了 16 秒 —— 而它也是唯一一次拿到 root 的。
- **结论：连上了却干不成事，是因为"root 重连"这一段比窗口还长。**

### 第 3 层 · 高置信：崩溃循环会把窗口从内部吃掉

直接证据：

- 12:29 窗口里，`pm enable` 前 8 条报 **`Could not access the Package Manager. Is the system running?`** → 说明**抓到时 PMS 已经死了**，那一刻"adb 能连"但"什么都做不了"。
- 13:51 抓到时 **uptime 只有 27 秒**，`=FRESH_FATAL=` 里 servicemanager 报 `mouse/backup/serial/assetatlas/appwidget/... died` 一长串。
- 也就是说：**窗口的长度取决于崩溃发生在启动的哪一帧，从来没有稳定过。**

### 第 4 层 · 中高置信：主机侧 21 秒陷阱（这是"人为错过"）

Windows 上 `adb connect` 打一个不存在的 IP，会走 TCP SYN 重试，**阻塞约 21 秒**。16:06 那次手动尝试就是被这个吃掉的。
后来改成"先 TCP 探测、命中才连"才解决 —— 这不是设备的锅，是工具的锅。

### 第 5 层 · 中高置信：找错门（IP / MAC 漂移）

- `.17`（旧 DHCP / 无线相关 MAC `8C:19:B4`）→ `.104`（有线新 DHCP，有线 MAC `2C:D9:74` / 后被识别为 `88-79-5b`）。
- 中途你把电视搬到华为路由器（另一个网段），监听脚本当时只扫 `192.168.50.x` → 那段时间的"连不上"是**敲错了门**。
- ARP 邻居表里 `.104` / `.17` 一度是 `00-00-00-00-00-00 Unreachable`（邻居表失效），**靠 IP 判断设备并不可靠**。v3 才补上"按 MAC `88-79-5b` 从 ARP 自动发现"。

### 第 6 层 · 中置信：16:07 之后窗口归零 = 换了故障模式

从 16:07 到 17:02，约 55 分钟、几十次断电重启，**一次端口都没开过**。

这不像"窗口变短"，更像**设备现在根本走不到联网那一步**：
- 要么是 init 更早的阶段就挂死（你说的"开机直接卡住、按遥控器没反应"）；
- 要么以太网 / `dhcpcd` 没起来；
- 要么它已经不再真正上电（电源板 / 主板保护）。

反过来讲，**如果它还是"崩了但网络起来了"，我们至少能探到端口**。现在连端口都没有 → 网络栈没起来 → 靠 ADB 救的概率在快速下降。

## 五、真正的崩溃原因：还没坐实，但有一个关键反证

**关键反证：13:31 那次把 12 个停用包全部 `pm enable` 还原成功（`LEFT_DISABLED=0`），重启后电视照样循环。**
这说明「停用」**不是**唯一原因，甚至可能不是主要原因。剩下两个未排除的嫌疑：

1. **`com.konka.ie` 缺失** —— 它被 `pm uninstall` 掉了，是带 `PERSISTENT` 标志的常驻进程。日志里别的相关包（另外 4 个）后来都回来了，只有 `ie` 一直没回来。Android 4.4 的 AMS 在启动时会去拉 `PERSISTENT` 应用，拉不到会持续报错/重启。
2. **`/data/system/packages.xml` 被手工改写过** —— 13:31 推回文件时 `chown` 报 `Read-only file system`。如果落盘的文件属主/权限不对（system_server 以 `system` 身份运行，读不到就起不来），这本身就能造成永久循环。

> 这两条都无法在无 ADB 的情况下证实。已拉回的证据还在：
> `boot.log.evidence`（491 KB）、`packages.xml.evidence`（91 KB）—— 值得离线读完，但**不会再改变当前该走哪条路**。

## 六、现在该怎么做（按性价比排序）

### 🥇 1. 走"不依赖 ADB"的硬件/固件路径（推荐，止损）

| 方案 | 怎么做 | 前置条件 | 评价 |
|---|---|---|---|
| **工厂菜单恢复出厂** | 信源切「模拟电视」→ 按菜单 → 遥控输入 `2008` → 软件调试/工厂菜单 → 找「恢复出厂 / 清空数据」 | 能进工厂菜单 | **首推**。所有改动都在 `/data`，清掉必回原厂状态 |
| **U 盘强刷（挖煤模式）** | FAT32 U 盘放对应固件 → 插非 3.0 口 → 断电 → 按住机身键上电 → 约 10 秒进入强制升级 | 后壳标签的**型号 + 物料号**（你拍的 `IMG_1392/IMG_1390`） | 最彻底，但固件必须精确匹配机芯 |
| **康佳售后** | 报机身唯一条码 | 无 | 零风险，2~3 个工作日 |

### 🥈 2. 继续蹲窗口，但把动作压到"一条命令"

现在 v3 在窗口里要做 `root → 等重连 → 写 /cache → 验证 → reboot`，**5~8 秒**，对 3~5 秒的窗口太长。
正确顺序应该反过来：

```
窗口一开 → 立刻 adb -s X reboot recovery （一条命令，约 1 秒）
         → 若 1.2 秒后还在线，说明 reboot 没被接受 → 再走 root + stage + reboot
```

理由：**recovery 是独立分区，不跑安卓框架，不会崩溃循环**。一旦进去它就稳定停住，后面有全部时间从容处理。
（我已按此逻辑写好 v4 并替换上线，见下。）

### 🥉 3. 低成本值得一试

- **机身摇杆组合键**：很多 MStar / 康佳板子是"按住机身键上电"直接进 recovery，不需要 PC。你说机身上只有一个摇杆，可以试试"上电时把摇杆推向某个方向并保持 10 秒"。
- **TTL UART 串口**：MStar 板子普遍留有调试串口（3~5 pin），接 USB-TTL 能拿到**不依赖安卓的 bootloader / shell**，是专业救砖路径。需要拆后壳 + 一根几块钱的 CH340 线。

## 七、这件事的方法论教训（值得记下来）

1. **一次动了 17 个包，违反"分批 + 每步验证"** —— 这是事故的直接原因。正确做法是先只动 `bootlogicproxy` 一个，重启验证，再往下走。
2. **`PERSISTENT` 标志的包绝不能 `uninstall`** —— 只能 `disable`。原项目 CleanYourTV 的硬性护栏里就有"禁止 `pm uninstall`"，这次是绕开了护栏手动执行的。
3. **国产定制 ROM 不能套用公开包名清单** —— 康佳在 CleanYourTV 的 280 份实测清单里**命中 0 条**，所有包名都是靠 `dumpsys package` 现猜的。
4. **"能连上"≠"能救"** —— adbd 活着只代表 init 活着；`pm` / `system_server` 死掉时，ADB 唯一能做的只有 `reboot recovery` / 推文件。这个认知如果早点有，第一次 12:29 的 26 秒窗口就该直接发 `reboot recovery`，而不是跑 12 条 `pm enable`。
5. **灾难恢复要先确认"哪条路不依赖故障组件"** —— 这次所有抢救脚本都依赖 ADB，而 ADB 恰恰是被崩溃循环切碎的那个。硬件路径（工厂菜单 / U 盘 / 串口）应该更早并行启动。
